# 《一人江湖》设计文档工作流

## 定位

设计决策必须**可追溯、可回滚、可复核**。本规范提供与既有"文档-代码-测试一致性"机制（Q2）平行的设计侧机制：决策登记 + 文档分层 + 审计闭环。

## 1. 决策登记表（ADR，移植自 sanguo-mud decisions.md）

在 `docs/decisions.md` 维护决策登记表：

- 每个设计决策有唯一编号 **DC-xxx**；文档引用时写「（DC-xxx）」，**不重述决策内容**。
- 表头列：编号 / 日期 / 标题 / 决策摘要 / 理由 / 影响文档 / 状态。
- 状态：✅ 已采纳 / 🔄 已被替代（见"被替代决策"） / ⛔ 已废弃。
- **被替代决策表**：记录旧决策被哪个编号替代及原因（变更历史，供追溯）。
- 只记录**决策与变更**；稳定事实（项目名、技术栈等）留在 charter/README，不进决策表。

新增决策流程：

1. 在 `docs/decisions.md` 登记（先给新编号）；
2. 更新受影响文档中的引用（写「（DC-xxx）」）；
3. **若决策含机制/数值生效口径**：同一任务按 `.cursor/rules/yjh-mechanics-sync.mdc` 更新 `mechanics.yaml`（pack+broken-pack）、schema 默认值、`numeric-baseline`（及必要时 protocol/catalog）；
4. 跑一致性校验（见 §4）。

**本项目已隐含的决策**（charter/计划中已定）建议回填为 DC-001 起的编号：H5 优先、服务端权威、无原始指令、单角色可重开、战术模板受控、离线挂机、赛季双轨榜、纯文本论坛、前期无支付、内容包驱动等。

## 2. 设计文档分层

| 层                   | 作用                           | 结构（移植自 sanguo 范例）                                                                                           |
| -------------------- | ------------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| **proposal**（提案） | 机制/内容取舍论证，先于实现    | 目的与边界 → 来源证据与适配结论（pkuxkx 源码事实/机制推断/本项目决策）→ 规则细节 → GUI 与状态要求 → 同步范围与未决项 |
| **spec**（规格）     | 面向实现的完整设计（如 UI/UX） | 设计结论 → 继承与超越 → 信息架构 → 视觉系统 → 核心交互 → 原型范围与验收 → 一致性审计                                 |
| **audit**（审计）    | 设计/实现与文档的一致性核验    | 审计概要 → 已修复阻塞项 → 关注项（分级）→ 通过项 → 修复优先级 → 多轮复核记录                                         |

- proposal 的"来源证据"必须可查证（pkuxkx 文件路径/行号或已有文档）；适配结论要写明"改了什么、为什么"。
- 设计文档相互引用一律用编号（DC-xxx 或 §章节），不复制内容。

## 3. 审计方法论（移植自 mobile-uiux-v1-audit.md）

- **多轮审计**：每轮记录日期与轮次；修复后进入"修复复核"轮，逐条确认已落地。
- **分级**：
  - 🔴 P0：阻塞项（设计与 PRD/文档冲突、年代/数值错误、功能缺失）——必须修；
  - 🟡 关注项：术语表达、功能覆盖、交互逻辑、文档自洽——建议修或确认；
  - 🟢 通过项：与文档一致的部分（列出，防止重复审计）。
- 每轮结束给出**修复优先级建议**；下一轮先核对上一轮修复是否全部落地。
- 审计对象可包括：设计文档 vs 原型/实现、PRD vs 规格、内容包 vs Schema。

## 4. 一致性检查

- 决策引用编号的完整性用脚本校验（移植 sanguo 的 `check-doc-consistency.js` 思路）：扫描文档中的「（DC-xxx）」引用，全部必须存在于 `docs/decisions.md`；`decisions.md` 的“影响文档”中提到的文档必须存在。
- 落地状态：**已完成**（E14.12）——`scripts/check-doc-consistency.js` + 根脚本 `pnpm test:docs-design`，CI quality 作业同步执行（与 `pnpm test:docs` 协议契约并列）。新增决策登记后跑 `pnpm test:docs-design` 即可自检。
- 与既有 Q2 机制的关系：协议契约（代码↔文档）管运行时契约；本规范管设计决策与设计文档；内容包校验管内容结构。

## 5. 检查清单

- [ ] 新决策已在 `docs/decisions.md` 登记（唯一编号 + 理由 + 影响文档）。
- [ ] 受影响的文档引用处更新为「（DC-xxx）」。
- [ ] 设计文档按分层结构撰写；来源证据可查证。
- [ ] 改动设计后运行一致性检查（若有脚本）全绿。
- [ ] 实现与设计不一致时，走 audit 记录而非静默修改。
