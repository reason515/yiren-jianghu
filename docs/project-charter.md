# 1. 项目定位

《一人江湖》是一款面向移动端的现代武侠角色扮演游戏：玩家在线进入各自独立的江湖世界，专注探索、剧情、PvE 成长、在线挂机、异步 PVP 与轻量社区互动。

- **体验定位**：在线但单人沉浸；玩家不会在地图中相遇或争抢资源。
- **产品形态**：文字叙事为主，地图、人物与战斗配合轻量插画和演出；不制作自由行走的 2D 场景。
- **交互原则**：不展示 MUD 原始命令行。探索、对话、战斗、修炼和任务均由结构化移动端 UI 操作。
- **独立性**：使用全新代码仓、全新账号和全新数据模型，不兼容现有 MUD 的账号、角色与 LPC 存档。
- **参考边界**：pkuxkx 仅作为机制与内容研究来源，不作为新游戏运行时，也不承诺全量复刻。

# 2. 平台与发布路径

## 2.1 阶段路径

1. **H5 邀请制封闭试玩**：先部署至服务器，邀请朋友体验并快速迭代。
2. **微信小程序正式渠道**：在核心体验、服务端稳定性和留存得到验证后适配。
3. **TapTap 小游戏**：作为后续渠道，复用服务端和跨端客户端能力。

## 2.2 跨端原则

- 客户端从第一天开始使用跨端约束开发，不走纯 Web 完成后整体重写小程序的路线。
- H5 与微信小程序共享游戏 API、规则、内容包和服务端数据模型。
- 不将浏览器 LocalStorage、Service Worker、DOM 专属能力或 H5 登录流程作为游戏核心依赖。

# 3. 技术架构

## 3.1 技术栈

| 层级 | 方案 | 说明 |
|---|---|---|
| 客户端 | Taro + React + TypeScript | 首先输出 H5，后续输出微信小程序 |
| 服务端 API 与游戏规则 | Node.js + TypeScript | 服务端权威处理角色、探索、战斗与结算 |
| 主数据 | PostgreSQL | 账号、角色、背包、任务、PVP、论坛、审计事件 |
| 异步作业 | Redis + Worker | 挂机、延迟结算、通知和后台任务 |
| 内容包 | Git 管理的 JSON/YAML | 地图、NPC、剧情、技能、物品与任务 |
| 部署 | Docker Compose | H5、API、Worker、PostgreSQL、Redis、反向代理 |

## 3.2 服务端权威

- 剧情推进、探索、战斗、挂机、PVP 和奖励全由服务端结算。
- 客户端只负责展示、收集玩家意图与订阅状态，不能作为角色存档或奖励判定来源。
- 断线后客户端自动重连，服务端恢复角色位置、任务状态、战斗状态和未读结算。

## 3.3 本地开发与真机验证

```text
Taro 本地构建
    ↓
H5 开发服务器 / 微信开发者工具
    ↓
本机 Docker Compose
  API + PostgreSQL + Redis + Worker
```

- H5 模拟和微信开发者工具用于高频调试。
- 微信开发者工具支持模拟器、断点、控制台、网络与存储查看、扫码预览和真机调试。
- 真机无法访问自身 `localhost`，调试时使用局域网 HTTPS 地址、临时安全隧道或预发布服务器。
- 每个迭代必须在 Android 微信真机验证登录、断线重连、前后台切换和挂机恢复。

# 4. 账号与角色

## 4.1 身份体系

- 服务端内部以平台无关的 `accountId` 作为账号主键。
- H5 封测使用邀请码和测试登录身份。
- 微信版本使用微信授权认证，并由玩家主动绑定至已有 `accountId`。
- 游戏角色名独立于微信昵称，使用唯一角色 ID 管理。

## 4.2 单角色与重开

- 每个账号仅有一个主角色。
- 玩家可二次确认后放弃当前角色并立即创建新角色。
- 被放弃的角色冻结 30 天，仅供风控与客服追溯。
- 冻结角色不可恢复、不可转移资产、不可参与排行榜、异步 PVP 或论坛身份展示。

# 5. 探索、战斗与挂机

## 5.1 手动探索

- 玩家手动探索时，对话、移动与物品使用均为结构化手动操作。
- 手动 PVE 战斗：普攻按节拍自动推进（仍经服务端意图结算）；绝招、回气、逃跑由玩家在适当时机手动触发（DC-037）。不隐式自动施法。
- 支持同场多名敌人（1vN，DC-038）。

## 5.2 在线挂机

- 挂机是服务端持久化作业，玩家切后台或 App 被系统终止后仍可继续。
- 玩家返回后查看挂机进度、战报和结算；客户端重连只恢复订阅与展示。
- 每次挂机具有时长上限、资源消耗、安全停止条件、失败条件和离线战报。
- 核心成长资源设置每日递减收益，避免无限挂机成为唯一最优玩法。
- PvE 战败不会掉落装备、货币或永久属性；挂机失败停止并记录原因，手动探索失败回到安全点并承受轻度恢复代价。

## 5.3 战术模板

- 玩家可维护多份可命名战术模板，供不同 PvE 挂机场景选用。
- 每次启动挂机时，玩家手动选择一份模板；任务启动后固化该模板版本。
- 模板由受控结构化模块组成：**条件 → 动作 → 冷却 → 优先级**。
- 可用条件包括气血、内力、状态、绝招冷却等；可用动作包括绝招、回气、恢复等。
- 不开放自由脚本、正则表达式触发器或客户端文本解析自动化。

# 6. 异步 PVP 与排行榜

## 6.1 异步 PVP

- 对战双方均为单个角色快照，不存在队伍或阵容。
- 异步 PVP 全程按角色已配置的 PVP 战术模板自动结算。
- 服务端保存角色属性、装备、绝招、模板版本与固定随机种子，保证战报可复盘与审计。
- 胜负仅影响赛季积分与赛季奖励，不掠夺货币、装备或成长资源。
- 首发限制每日挑战次数，防止刷分和无节制消耗。

## 6.2 排行榜

- **长期展示榜**：角色成长、收集与剧情成就。
- **赛季竞技榜**：异步 PVP 与活动积分，按 4 至 8 周赛季结算并重置名次。
- 赛季制让后进入的玩家也拥有竞争机会，避免长期挂机角色永久垄断。

# 7. 内置论坛

## 7.1 首发功能

- 分区浏览、官方公告、发帖、评论、点赞、举报。
- 仅支持纯文本内容。

## 7.2 明确不做

- 私信、群聊、图片上传、玩家交易信息。
- 任何以论坛替代实时社交或交易市场的功能。

## 7.3 治理要求

- 服务端敏感词过滤、发帖与评论频率限制、举报队列、管理员审核与封禁记录。
- 论坛身份与游戏账号绑定，角色放弃后原身份下线。

# 8. 内容生产与 pkuxkx 参考治理

## 8.1 内容包机制

- 地图、NPC、剧情、技能、物品和任务采用版本控制的 JSON/YAML 内容包。
- 提供模式校验、引用校验、构建检查、预览和回滚能力。
- 前期不建设运营 CMS；内容规模和协作需求明确后再评估。

## 8.2 参考内容登记

任何参考 pkuxkx 的候选内容均须先登记为以下三类：

| 类别 | 处理方式 |
|---|---|
| 可借鉴机制 | 重新设计并实现为新游戏的结构化规则 |
| 需改写的设定与文本 | 保留灵感来源，重新编写、重新命名并独立验收 |
| 需确认授权的代码或素材 | 未确认权利前不得复制进入新仓库 |

每项进入新仓库的内容均应保留来源、改写记录、依赖与权利状态。

# 9. 封测运维、测试与验收

## 9.1 封测规模

- H5 首批邀请 20 至 50 名活跃玩家。
- 先验证玩法闭环与正确性，再按周复盘后分批扩容。

## 9.2 核心验收指标

1. 新手闭环完成率。
2. 次日留存。
3. 挂机断线恢复成功率。

首轮不以付费转化或高并发规模作为目标。

## 9.3 上线前置条件

- 数据库每日备份与定期恢复演练。
- 结构化日志、健康检查和基础监控。
- 数据库与 Redis 不暴露公网。
- Docker 镜像版本、环境变量模板、数据库迁移脚本和备份脚本可复现部署。
- 新旧服务器迁移可通过镜像、配置与数据备份完成；不可逆迁移前先执行备份与恢复验证。

# 10. 明确暂缓的决策

下列内容将在后续单独讨论并形成筛选清单：

- 从 pkuxkx 中选择哪些区域、门派、任务、技能、装备、NPC 和剧情。
- 新游戏的世界观、地名、人名、阵营与文本重写范围。
- 首个垂直切片的具体内容和数值节奏。
- H5 封测后的微信小程序发布时间与服务器迁移时间。

# 11. 下一步

在创建 GitHub 仓库后，优先建立单仓基础结构和领域数据契约：

1. 账号与角色。
2. 角色状态、背包和安全点。
3. 手动战斗动作与服务端结算事件。
4. 战术模板与挂机作业。
5. 异步 PVP 快照与战报。
6. 内容包 Schema、校验与权利登记。
7. H5 邀请码认证、Docker 本地环境、备份与健康检查。
